# Validation modes and leakage prevention

Record scope and input allowlists before running a test. Keep these modes separate:

1. **Mechanical replay/regression:** known completed artifacts may be read. Rebuild inventory and audit/package their citations under the new portable workflow; compare source/module/function/table coverage, hashes, rules, data and unknowns with the reference. This tests adaptation and preservation, not rediscovery ability.
2. **Blind semantic run:** a fresh evaluator receives only the skill and recovered repository, with no prior specification/answers/chat history. It discovers systems, performs worker analysis and cross-review, audits and packages its result. It may be a declared subset or a full run; state exactly which. Freeze output hashes and logs before the comparator sees the reference. Separate a blind evaluator from the baseline comparator.
3. **Second-input run:** use the same installed skill on another recovered repository. Discover that input's actual systems and check no first game's IDs/content are imposed. Full inventory with sampled semantics is not full-game generality. Shared framework code across two games is not evidence that unique gameplay was analyzed.
4. **Independent installation:** extract the distribution to a fresh directory, run helpers/tests using only relative paths and the declared Python requirements. Verify manifests, source/bytecode citations after relocation and actual worker execution where available. Do not reuse a prior final package as if generated by the skill.

Record worker IDs, assigned paths, log scope and failures. A prompt claiming an allowlist is not an OS sandbox; report that trust boundary. If the host cannot run independent workers, mark blind/parallel behavior untested rather than simulating successful agent output.

Comparison uses identities and concepts, not quotas. System grouping, claim splitting and citation count may differ. Report preserved/lost source coverage, rule/data disagreements, newly exposed unknowns, dropped certificates, and claimed versus computed scope. Do not optimize toward a previous result's counts. A matching count is not proof of correctness.

User-facing classification:

- FULL SUCCESS requires an actual fresh-agent skill+repository workflow through discovery, parallel analysis, independent cross-review, audit and usable package. State tested input/scope; it does not mean every server behavior is known.
- PARTIAL SUCCESS if packaging/mechanical verification works but full independent execution or cross-game generality is not demonstrated.
- FAILURE if the package merely copies an old report, supplies generic prompts without tested mechanics, or conceals failed/untested runs.

The core distribution has no game-specific reference answer. Historical regression reports and answer-aware comparisons belong in a separate validation bundle, outside blind workers' allowed inputs.

## V1.1 bounded completeness evaluation

Do not rerun a whole game merely to test a completeness change. Use source-only scouts on bounded real interaction slices in the regression input and a different game; keep suspected omissions/answers outside their prompts and skill. Freeze observations before comparison. Then adjudicate missing relationships, wrong mappings, blanket UNKNOWNs, false positives and known missed controls. Record files/functions/searches/time, untraced scope and any prompt/access leakage. Known sentinels give local recall only; an unseeded source pass has no exhaustive ground truth. Separately run generic mutation tests for dropped obligations, wrong reciprocal links, false UNKNOWN, missing function entries, inflated completion and frozen-review tampering. Passing these accounting controls does not prove semantic discovery. Fresh-install tests must execute the shipped CLI/gate and verify the packaged ledger survives relocation.

For function coverage changes, test generic-rationale rejection, borrowed/null/out-of-range citations, missing steps, unsupported review promotion and separate author/independent support. Test ownership gaps/duplicates, shared-payload ownership decisions, canonical cross-system rule IDs and failed-integration no-write behavior. Sample actual TRACED records against source to assess whether prose follows branches and effects; passing structural checks cannot measure that truth. Report declared states, supported traces, source-review traces and reviewed functions separately. Do not relabel a historical run as newly source-reviewed merely because it passes a new bookkeeping command.
