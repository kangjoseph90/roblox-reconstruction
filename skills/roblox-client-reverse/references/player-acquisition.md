# Raw Player capture

`capture --pid PID [--place PLACE_ID] --game GAME` captures the Place the Player is in into `GAME/captures/<PlaceID>/`. It does not launch a Player, build recovery tools, decompile bytecode, or overwrite an existing capture. See [player-control.md](player-control.md) for the discover/open/screenshot sequence and [acquisition.md](acquisition.md) for recovery.

## Current Place and transfers

Games may move a joining Player to another Place of the same Universe (for example to a saved world). Capture therefore does not trust the requested Place. Structure validation accepts the Universe ID together with exactly one Place ID from `places.json`, and the DataModel holding them names the current Place. Structure validation itself reads sample script buffers as layout witnesses, so it must succeed in the current Player first. The Place is identified before any script buffer is captured or stored:

| Current Place | Result |
|---|---|
| The requested Place | captured as usual |
| Another catalogue Place without a capture | captured into `captures/<actual>`; the result has `requested_place_id`; the requested Place's `entry` becomes `redirected` with `redirected_to` when this is the Player `open` recorded as new for it, otherwise the result reports `requested_place_unconfirmed` |
| Another catalogue Place that already has a capture | `skipped` before collecting script buffers; the requested Place is marked `redirected` under the same condition; `places.json` is brought in line with a finished capture on disk (for example after an interruption), and a capture failing its integrity check is reported as `blocked` |
| An existing failed or unfinished attempt without `--retry-failed` | `blocked` (exit 2) with the reason |
| No catalogue Place, or another Universe | failed structure/identity validation; never a skip or a redirect |

Without `--place`, capture takes whichever catalogue Place is open. The actual Place keeps its own `entry` record. A redirect is recorded only when the requested Place's entry names this Player as the new process `open` launched (`launched_by_open`, same PID and creation time); otherwise every result for that request (`pass`, `skipped`, `blocked`) reports `requested_place_unconfirmed` and the requested Place's entry is unchanged. After collecting buffers, capture scans for DataModels again and reads the Place and Universe from memory. The attempt fails if the matching DataModel is missing, ambiguous, differs from the first observation, or if a valid DataModel appeared or changed its Place/Universe, whatever Place it holds. Checks apply in this order: a confirmed change fails the attempt first, including a DataModel first seen in the final scan when the first scan was complete. Otherwise, if either scan was incomplete (budget, candidate limit, unreadable bytes or an interrupted region walk) or a DataModel header could not be read in full, `place_validation` is `incomplete`, because a replacement DataModel cannot be excluded; a DataModel first seen after an incomplete first scan is reported this way, since that scan may simply have missed it. An `incomplete` validation makes the collection `partial`, or `failed` if no buffer passed its checks. `evidence/place-validation.json` records both observations and the final scan coverage. These are two observations of a non-atomic snapshot. Refresh `places` first if a game may move Players to a Place the catalogue does not yet list.

Each attempt is written to `captures/.attempt-*` and moved to its Place directory once that Place is known. A failure before the Place is identified is stored under the requested Place when that directory is free; otherwise the attempt stays under its `.attempt-*` name and the result names it in `path` and `kept_aside`, with status `failed`, or `blocked` when its collection succeeded. A kept-aside attempt is not referenced by `places.json` and is not used by `recover GAME`. A capture directory that is, or contains, a link (symlink or Windows junction, including one whose target is missing) is never written to or recorded. Storing an attempt holds `captures/.<PlaceID>.storing`; another attempt for the same Place meanwhile is kept aside (`blocked`, or `failed` if its own collection failed). An identification in another Universe than `game.json` fails the attempt; it is neither a skip nor a redirect. Remove a leftover lock only if no capture is running. Interrupted attempts may leave `.attempt-*` directories; they are not referenced by `places.json` and can be removed.

If a prior attempt failed before any raw/bytecode buffers were written, `--retry-failed` can explicitly retry that same directory after its integrity passes. Previous diagnostic bytes are retained in `evidence/attempt-errors.json`; no capture-version folders are created. The flag cannot replace a capture containing buffers. `recover CAPTURE --out DIR` refuses a failed capture (`failure_stage: capture_failed`), including one that stopped before writing a dump, rather than recovering its buffers.

`scripts/windows_access_probe.py` is a standalone Windows diagnostic: it reads a marker from an owned child process and, with `--pid`, only the Player's executable DOS header. `scripts/macos_access_probe.c` is a macOS prerequisite test: `--self-test`/`--child-control` read a marker in its own test program, and `--pid` reads only 16 bytes of dyld loader metadata if a task port is granted. Neither collects game data.

The collector uses read-only process access. It validates the executable, supported structure, target Place and Universe identity, stable script buffers, and supported RSB1 integrity/encoding before saving raw observations. Unlisted executable hashes may be attempted, but are not certified by version. Ambiguous layouts, unsupported ABI/encoding, insufficient witnesses, unreadable data or failed identity checks stop or limit capture. Normal process exit does not establish success; reports retain partial/missing/unknown scope. See [adaptive-builds.md](adaptive-builds.md) for assumptions and bounds.

Each capture preserves the observed instance metadata and provenance, original encoded byte buffers, capture evidence and file inventory. Recovery later checks hashes and approvals on those original buffers. Convenience fields such as embedded source or decoded bytecode do not authorize recovery.

Per-script diagnostics record the inventoried address, class, name and parent, along with the before/after observations and timestamps. Path revalidation can report `node_unreadable`, `class_changed`, `name_changed`, `parent_chain_invalid`, `wrong_datamodel`, `object_destroyed_or_replaced` or `unknown`. The destruction/replacement label denotes a self-pointer or vtable mismatch. Workspace scripts are checked first because their instances can be transient.

The snapshot is non-atomic and covers observed replicated LocalScript/ModuleScript containers. It does not establish full replication, script execution, server-side logic, coverage of Places a game never transfers to, or RunContext Client Script support. No recovered game code is run. Keep syntax, function CFG, module CFG and behavior states distinct; game behavior remains untested unless supported by separate direct evidence.
